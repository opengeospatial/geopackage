=== Description

This extension defines the ability to optionally split data layers stored in GeoPackages using a deterministic approach to organize the directory structure and naming individual GeoPackage files.

Each data layer can also be associated with a _GeoDataClass_ URI using the https://docs.ogc.org/DRAFTS/24-049.html[Semantic Annotations] extension so that clients can easily find a particular class of data in the indexed GeoPackages.
For tiled vector data using the https://docs.ogc.org/DRAFTS/24-048.html[Tiled Feature Date extension], this can be done both at the level of the multi-layer tileset, as well as at the individual component vector layer.

This extension defines tables describing the GeoPackage configuration, allowing to best balance tradeoffs between the number of GeoPackages created and the file and table sizes within each GeoPackage for a particular dataset or use case.

The simplest option is storing everything in a single GeoPackage. Data layers can also be organized into multiple _packages_ stored together. A tile level grouping count can also be specified to split these packages into GeoPackages storing a partial tile pyramids consisting of that many levels sharing a single base tile. This approach limits the size of individual GeoPackages while balancing the number of files.

Conforming clients can open the primary GeoPackage and access the data regardless of which particular configuration of this extension is used, to suit a variety of datasets and use cases ranging from global high resolution repository spanning petabytes of data to small local extracts for mobile use. Regardless of the configuration option used, a client can easily find a particular data layer, without the need to look up an index for a particular area.

=== Definitions

- A *_level_* corresponds to a 2DTMS Tile Matrix
- A *_package_* represents one or more data layers packaged together, either as a single GeoPackage, or in multiple GeoPackages grouping a partial tile pyramid of zoom levels (from a minimum to a maximum level), or of untiled vector data (in Features tables).
- A *_GeoDataClass_* (previously called a _Stylable Layer Set_) is a URI which has an associated schema (consisting of specific data layers, each with a schema defining specific fields and associated semantics); can be any type of geospatial data (coverage, vector features, 3D models...)

CREATE TABLE gpkgext_hierarchical_gpkg_index(
   table_name REFERENCES gpkg_contents(table_name) NOT NULL,
   package_id REFERENCES gpkgext_hierarchical_gpkg_packages(id) NOT NULL,
   max_level INTEGER

CREATE TABLE gpkgext_hierarchical_gpkg_packages(
   id INTEGER PRIMARY KEY,
   name TEXT UNIQUE,
   level_grouping_count INTEGER,
   max_grouping_level INTEGER,
   tms_id INTEGER REFERENCES gpkgext_tile_matrix_set(id)
)

=== Sub-GeoPackages naming and directory structures

The file and directory naming are deterministic and simple to compute algorithmically, without having to lookup any index to discover arbitrarily named files.

==== File names

The GeoPackage filenames follow the following template based on the package name, the coarsest tile in that package forming the basis of the partial tile pyramid for that
GeoPackage, along with the level of the finest level tile that would normally be placed into this GeoPackage (excluding insets):

`{packageName}_L{gpkgMinLevel}_R{gpkgTileRow}_C{gpkgTileCol}_L{gpkgMaxLevel}.gpkg`

An example based on the GNOSIS Global Grid: **Imagery_L12_R2607_C2858_L18.gpkg**

[requirement]
====
[%metadata]
identifier:: /req/core/file-names
description:: For naming GeoPackage files grouping tiled content referenced by the primary GeoPackage
part:: The file names of GeoPackage files grouping tiled content referenced by the primary GeoPackage SHALL follow the template
`{packageName}_L{gpkgMinLevel}_R{gpkgTileRow}_C{gpkgTileCol}_L{gpkgMaxLevel}.gpkg` where:
- `{packageName}` refers to the package name as specified in the `name` field of the `gpkgext_hierarchical_gpkg_packages` table,
- `{gpkgMinLevel}` refers to the lowest level tile included within the grouping inside the GeoPackage,
- `{gpkgTileRow}` refers to the row of that lowest level tile (based on the TileMatrixSet for that package, for both CDB 1 and GNOSIS Global Grids they are counted from top/North to bottom/South),
- `{gpkgTileCol}` refers to the column of that lowest level tile (based on the TileMatrixSet for that package, from left/West to right/East), and
- `{gpkgMaxLevel}` refers to the maximum level tile normally included within the grouping inside this GeoPackage (excluding insets).
For the deepest sub-directory, this will be the same value as the package `max_level` specified in the index.
====

==== Directory structure

The directory organization, which limits the number of GeoPackage files and sub-directories that could exist within a single directory based on a particular level
grouping count, follows the template:

```
{packageName}/
   L{parentMinLevel}_R{parentTileRow}_C{parentTileCol}/
      L{parentMinLevel}_R{parentTileRow}_C{parentTileCol}/
         ...
```

==== For even more deterministic naming

To facilitate extraction from a large global high-resolution dataset and easily merge these extracted sub-datasets as well as the ability to augment these base datasets with additional more detailed insets, without repackaging the entire dataset, the following solutions are proposed:

* The publisher of a large repository of data could define a profile pre-establishing the fixed package name, level grouping count and maximum package level for a specific GeoDataClass.
* When inset data is added to a dataset, these could go beyond the regular maximum level specified for the package (package `max_grouping_level`). As such these inset tiles are always grouped together with the tiles of the regular maximum level.

=== Profiling this extension

This extension addresses the use cases of splitting large datasets into multiple GeoPackages for efficient access using deterministic naming.
Some example datasets where this would be convenient:

* https://www.ogc.org/standards/cdb/[OGC CDB] (a model and structure for a virtual detailed representation of the earth),
* OrdnanceSurvey Master Map,
* OpenStreetMap Planet OSM,
* ESA sentinel-2

This indexing mechanism allows to describe multiple configurations:

- Choosing whether each GeoDataClass is in its own package, or together with data for other GeoDataClasses
- Choosing whether a particular package is organized by level groups or as a single GeoPackage

These options allows to define profiles that can balance the simplicity of working with a single container vs. the impracticality of dealing with huge files, and to adapt this to a particular dataset and usage, while a client implementing this extension will still be able to easily support all profiled configurations in a generic manner.

A particular profile could prescribe a particular grouping number for each GeoDataClass to be stored.
Initial experiments used a grouping of 7 for imagery stored as JPEG and a grouping of 6 for elevation stored as GeoTIFF.
A grouping of 5 was used when storing all datasets (3D models, vector, elevation, imagery) in the same package.
Different encoding formats with different compression ratio may work best with different values.

For users at the edge and smaller datasets over a small area, storing everything in a single GeoPackage is most convenient.  This approach could be result from an export from a larger dataset, where only the resolutions and the boundaries of the data needed are stored and delivered to an end user. Users at the edge are such individuals as field operatives using mobile devices with limited battery, memory, storage and processing capabilities as well as Delayed/Disconnected, Intermittently-connected or Limited bandwidth (DDIL) environments.

For Modeling and Simulation uses, as well as data repository cases, the Level grouping functionality can be used, and related data layers can be organized as a single package.  This involves storing a region of the world at a set of zoom levels, or levels of detail, within a single GeoPackage, with a specified file and directory naming scheme.  This approach would allow for faster access to data at specified areas and zoom levels.  This approach would also lend itself to concurrent access and editing for data repository maintainers.
